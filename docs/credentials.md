# 认证状态、重新登录与导入导出（macOS 1.7.1-preview.1）

## 认证状态

每个账号卡片的名字旁边有一个状态徽标：

| 徽标 | 含义 | 怎么处理 |
| --- | --- | --- |
| 绿色「认证有效」 | 官方服务接受了这份登录（最近一次额度查询或诊断成功） | 无需处理 |
| 灰色「待验证」 | 这份登录还没被官方服务检查过（刚保存、刚导入或刚同步） | 稍等几秒，会自动查询一次 |
| 黄色「令牌已过期」 | 访问令牌到了自己的到期时间 | 切换到该账号时，Codex 会用刷新令牌续期；若 Codex 要求登录，点「重新登录」 |
| 红色「登录已失效」 | 访问令牌**未到期**就被官方服务拒绝（401） | 点卡片上的「重新登录」 |

失效的账号还会：卡片边框变红、出现带「重新登录」按钮的提示条、列表顶部出现汇总横幅、侧边栏「账号空间」出现红色标记、菜单栏账号后面标注「登录已失效」。原来的「切换并重启」挪到「…」菜单里的「仍然切换并重启…」。

判断依据只有两样：访问令牌里的到期时间（本机解码，不当作身份证明），和官方服务对**这一份**登录的回答。回答按访问令牌的短哈希（指纹）绑定。凭据一换（同步、重新登录、导入），旧的回答就不再适用，状态先回到「待验证」，再自动重新检查。

栖言自己从不使用刷新令牌，所以「令牌已过期」不等于刷新令牌也失效。那要等 Codex 续期时才知道。

`accounts.json` 里只新增了非机密字段：`stamp`（指纹、签发时间、到期时间）、`verdict`（接受/拒绝、指纹、时间）、`credentialSource`、`credentialUpdatedAt`。不含任何令牌文本。

## 重新登录后为什么以前不更新、现在怎么处理

以前有两个原因：

1. **账号正在 Codex 中使用时重新登录**：新登录保存进钥匙串后，Codex 手里仍是失效的旧 `auth.json`。之后点切换或「更新登录备份」，旧文件会把刚保存的新登录覆盖掉。
2. **Codex 自己续期或重新登录后**：栖言只在下一次切换时才把新登录存进钥匙串，卡片上的旧错误也一直留着。

现在的规则：

- **新旧比较**：每份登录取访问令牌签发时间和 `last_refresh` 中较新的那个时间。自动路径（同步、切换前备份、更新登录备份、导入）只在确实不更旧时才替换。两边都没有时间时按原来的方式更新。只有你主动完成的浏览器登录才无条件替换。
- **实时同步**：栖言每 2 秒检查一次 `auth.json` 的文件状态（只调用 stat，不读内容），切回栖言时也会检查一次。发现 Codex 写了新登录，就在几秒内存进对应账号，然后自动重新验证。不会自动新增未保存的账号。
- **载入新登录**：如果钥匙串里的登录比 Codex 正在用的更新，当前账号卡片会出现「载入新登录…」。确认后退出 Codex，用新登录替换旧文件，再重新打开。重新登录的正好是当前账号时，栖言会直接问你要不要载入。
- **登错账号保护**：从卡片点「重新登录」时，如果浏览器里登的是另一个账号，会先提示，可以另存为新账号或取消。

## 导入与导出

入口：账号列表上方的「导入 / 导出」，或菜单栏「账号 → 导入账号… / 导出账号…」，或卡片「…」菜单里的「导出此账号…」。

- **导出**：选择账号，设置至少 8 位的密码，保存为 `.stillcodex` 文件。导出的是每个账号最新的一份登录：当前账号取 Codex 正在用的那份，除非钥匙串里的更新。
- **导入**：选择 `.stillcodex` 文件并输入密码，或者直接选另一台电脑的 Codex `auth.json`。导入前会逐个列出「新增 / 更新登录 / 已是同一份 / 跳过（本机已有更新的）」。导入只写入栖言的钥匙串记录，不改动 Codex 当前的 `auth.json`。

### 使用须知

- 文件里是账号的登录凭据。拿到文件和密码的人可以直接使用这些账号。文件和密码请分开发送，用完删除。
- **导出的是同一份登录会话，不是新的登录**。两台设备都在用时，先续期的一方会让另一方的刷新令牌作废，Codex 会提示 *refresh token was already used*，需要重新登录。适合「搬到另一台电脑后不再在原电脑用」。长期两边都用，建议在另一台设备单独登录一次。
- 已失效的登录导出后在对方那里同样无法使用。
- 账号归属和使用条款以 OpenAI 的规定为准。

### 文件格式（供 Windows 版实现对齐）

```json
{
  "format": "still-codex-accounts",
  "version": 1,
  "kdf": { "name": "PBKDF2-HMAC-SHA256", "iterations": 600000, "salt": "<base64, 16 bytes>" },
  "cipher": "AES-256-GCM",
  "nonce": "<base64, 12 bytes>",
  "ciphertext": "<base64>",
  "tag": "<base64, 16 bytes>",
  "createdAt": "<ISO 8601>"
}
```

- 密钥：`PBKDF2-HMAC-SHA256(UTF-8(NFC(password)), salt, iterations, 32 bytes)`。读取时接受 10 万到 1000 万次迭代。
- 附加认证数据（AAD）：ASCII 字符串 `still-codex-accounts/v1`。
- 明文是 JSON：`{ "app": "...", "exportedAt": "<ISO 8601>", "accounts": [ { "label", "email", "plan", "auth": "<base64 编码的原始 auth.json 字节>" } ] }`，最多 200 个账号。
- .NET 对应：`Rfc2898DeriveBytes.Pbkdf2(..., HashAlgorithmName.SHA256, 32)` 和 `AesGcm`（标签单独存放，16 字节）。

## 验收状态

- 新增自测：`AuthTests`（令牌时间解析、状态判定、较旧不覆盖较新、实时同步、判定绑定指纹、加密导出往返、错误密码和篡改拒绝、导入分类与合并），另有 `DiagnosticsTests` 对 401 的标记。
- Apple Silicon Mac 本地编译并运行了虚构账号回归，包含新加的 `ExperienceTests`；没有调用真实账号模型、消耗重置卡或切换当前 Codex。完整记录见 `macos-ux-validation.md`。
- 真实账号的「重新登录 → 载入新登录 → 重启」和跨设备导入，需要在真机上核对。
- Windows 版尚未跟进。

## 1.7.1 交互更新

- 新增「验证中」「待解锁」「验证未完成」状态；通用网络/协议错误不是登录撤销证据，已确认的拒绝也不会被随后网络失败冲掉。
- 重新登录优先中断当前后台查询，验证这份新凭据。结果按凭据指纹匹配，旧请求返回不覆盖新状态。验证仅查询额度，跳过自动预热。
- 后台 Keychain 查询使用 per-call 禁止交互策略，手动解锁才允许系统授权；不使用进程全局授权开关。旧文件型 Keychain 兼容查询保留 `kSecUseAuthenticationUIFail`，该常量在新 SDK 中有弃用警告。
- 密钥只短时缓存，定时到期或锁屏/休眠时清除应用内缓存；这是缓存释放，不代表操作系统内存的可证明清零。
- 切换有四阶段提示，安全等待 Codex 退出，先写持久回滚再替换登录；启动失败则恢复。耗时仍取决于 Codex 的正常退出与启动。
- 首次手动解锁或签名变化仍可能要求系统授权；固定 Developer ID 签名有助于稳定应用身份，但该本地包仍是 ad-hoc 签名，未公证。
